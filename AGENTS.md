- Onboarding checklist items are never deleted: retired items get `active=false` (kept as history, ignored by stage advance); `applies_to_types` restricts an item to onboarding types; `completion_rule` (handoff_form / feedback_survey / monthly_report) items are concluded only by DB triggers — why: preserve in-flight client history and enforce gates server-side.
- Occurrences (timeline_entries.is_occurrence) are never physically deleted: cancel via cancel_occurrence (resolution_status='cancelada'); edits go through edit_occurrence (audit_logs with record_id + reason) and CS treatment through occurrence_action — why: server-enforced permissions and an immutable trail.
- /execucao is the single execution module (tabs: tarefas, onboarding, calendario) embedding TaskCenter and Onboarding via an `embedded` prop; /tarefas and /onboarding only redirect; task progress notes live in task_updates (author set by trigger) — why: one place for management + execution without duplicating logic.
- Permissions: access_profile sets defaults (profile_default_permission); internal_user_permissions rows are per-user overrides (granted true/false); always check via has_permission('<module>.<action>') in RLS/RPCs and useMyPermissions/usePermission in UI — why: per-person flags without new roles.
- Onboarding detail presentation reuses ChecklistItemRow in both stage and execution panels; description, execution steps and support materials map to the existing definition fields, while task updates remain available below supporting content — why: keep one implementation without changing stored history or completion rules.
